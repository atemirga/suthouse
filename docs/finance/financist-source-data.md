## 1. Справочник статей ДДС (с маппингом на ОПиУ)

Финансист использует трёхуровневую категоризацию: **Группа → Категория → строка ОПиУ**.

Группы (4 шт):
- Операционная деятельность (1.xx)
- Инвестиционная деятельность (2.xx)
- Финансовая деятельность (3.xx)
- Техническая операция (4.xx — перемещения)

Категории верхнего уровня (10):
- ОПЛАТА ОТ ПОКУПАТЕЛЕЙ
- ЗАКУП ТОВАРА
- РАСХОДЫ НА ЗАКУП (логистика-в-склад, таможня)
- БИЗНЕС РАСХОДЫ (аренда, коммуналка, расходники, ремонт, прочее адм.)
- РАСХОДЫ НА СОТРУДНИКОВ (ЗП всех типов, бонусы, обучение, корпоративы, налоги ФОТ)
- БАНКОВСКИЕ КОМИССИИ (комиссия банка, эквайринг)
- ТРАНСПОРТНЫЕ РАСХОДЫ (доставка клиентам / от клиента, парковка, ГСМ, содержание ТС, ремонт ТС)
- РАСХОДЫ НА IT ИНФРАСТРУКТУРУ И СВЯЗЬ
- РАСХОДЫ НА МАРКЕТИНГ
- НАЛОГИ (КПН)
- ИНВЕСТИЦИОННЫЕ РАСХОДЫ
- ФИНАНСОВЫЕ РАСХОДЫ

## 2. Эталонная «В/С» (выручка из 1С по месяцам)

Финансист берёт из 1С три компонента и складывает их в «Итого» (= `Realizacia.totalAmount` нашей системы):

| Месяц | Выручка (товары) | Скидка наличка | Доставка | Итого | Учтена с/с |
|---|---:|---:|---:|---:|---|
| окт.'25 | 140 267 910,00 | −143 478 | 2 392 150,00 | 142 516 582,00 | ✓ |
| ноя.'25 | 193 020 164,50 | −228 690 | 2 778 300,00 | 195 569 774,50 | ✓ |
| дек.'25 | 208 062 436,00 | −301 969 | 2 621 800,00 | 210 382 267,00 | ✓ |
| янв.'26 | 220 290 205,00 | −455 992 | 2 480 280,00 | 222 314 493,00 | ✓ |
| фев.'26 | 261 212 632,37 | −1 313 004 | 2 591 020,00 | 262 490 648,37 | ✓ |
| мар.'26 | 267 966 484,63 | −341 354 | 3 406 110,00 | 271 031 240,63 | ✓ |
| апр.'26 | 198 334 620,11 | −133 871 | 2 484 340,00 | 200 685 089,51 | ✓ |
| мая'26 – янв.'27 | — | — | — | — | (план) |

**Соответствие нашим таблицам (`Realizacia` / `RealizaciaItem`):**
- **«Выручка» (140 267 910 за окт)** = `SUM(RealizaciaItem.quantity * RealizaciaItem.price)` — gross прайс-листа.
- **«Скидка наличка» (−143 478 за окт)** = `SUM(quantity*price − amount)` — inferred discount по позициям.
- **Выручка − Скидка = `SUM(RealizaciaItem.amount)` = `Realizacia.itemsAmount`** (наше новое поле для ОПиУ).
- **«Доставка» (2 392 150 за окт)** = `Realizacia.totalAmount − itemsAmount` — услуги в заголовке документа (не товары).
- **«Итого»** = `Realizacia.totalAmount` (= СуммаДокумента из 1С) — то, что клиент по факту платит. Используется в дебиторке.

### Уравнение, которое держит систему «честной»

```
header.totalAmount  =  Σ(items.quantity × items.price)  −  Σ(item discounts)  +  delivery_services
                    =  «Выручка» финансиста            +  «Скидка»            +  «Доставка»
```

Все 7 месяцев сходятся в копейках. Если когда-нибудь в будущем `totalAmount ≠ itemsAmount + delivery_from_services`, значит, ломается одно из двух — либо синк услуг в Реализации, либо сама загрузка items.

### Структурное различие категорий ОПиУ — финансист vs наша система

**Категории финансиста (7 групп):**

4. Прямые постоянные (ГСМ + парковка + содержание ТС + инвентарь + типография)
5. Коммерческие (ЗП менеджеров + бонусы прод. + маркетинг)
6. Административные (аренда офиса + коммуналка + ЗП адм + банк + IT + связь + офис + обучение + командировки + корпоративы + налоги ФОТ + представительские)
7. Расходы ниже EBITDA (налоги на прибыль + амортизация)

**Наши категории (`OpiuCategory` enum):**
revenue, cogs, var_expenses, payroll, rent, marketing, admin, logistics, taxes, interest, other_income, other_expense, capex, financing_in, financing_out

**Маппинг между моделями** (что нужно будет сделать, когда подойдём к этому):
- Финансист **разделяет ФОТ** по типу персонала (производство/коммерч/админ) — у нас всё в одной `payroll`. Нужно либо разбить `payroll` на под-категории, либо мапить через имя статьи.
- Финансист **разделяет ОКЛАД и БОНУС** отдельными строками — у нас они слиты в одной DDS-статье 1.09/1.10/1.11/1.12. Нужно отдельное поле/маппинг на бонусную часть.
- Финансист **разделяет транспортные** на «Общепроизводственные» (1.17 общий транспорт, 1.35 ремонт ТС) и «Прямые постоянные» (1.19 ГСМ, 1.18 парковка, 1.20 содержание). У нас всё в одной `logistics`.
- **Источник «ЗП ведомость» и «ЗП формула»** — у финансиста часть ЗП считается по формулам, не из ДДС. Это значит, реальные начисления могут отличаться от выплат (накопленный к выплате остаток).
- **«Источник: формула»** для 1.07 Аренда офиса, 1.08 Коммунальные — финансист считает их «начислением», а не «оплатой» (метод accrual вместо cash). У нас они идут из ДДС cash-методом, поэтому будут «прыгать» по месяцам.

### Ключевое замечание

**ФОТ у финансиста — метод НАЧИСЛЕНИЯ**, не кассовый:
- Сумма «начислено» вычисляется отдельно от платежей в 1.09/1.10/1.11 (DDS).
- Разница = «Кредиторская задолженность по ЗП» = деньги, которые мы должны сотрудникам, но ещё не выплатили.
- Налоги тоже считаются по начислению, отдельно от 1.37 (DDS).

Для нашей системы это значит: **прямой импорт ДДС-выплат как ФОТ — даёт другую цифру** (кассовый метод), отличную от финансиста. Чтобы сойтись 1:1, нужно либо:
1. **Импортировать ведомость ЗП** отдельно (новая модель `PayrollAccrual`), и в ОПиУ брать её, а не DDS.
2. **Использовать `AccrualRule`** для статей 1.09/1.10/1.11 — но это работает только если выплата кратна 1 месяцу, тут сложнее (бонусы заморожены, налоги отдельно).

Вариант 1 точнее, но требует второго источника данных (Excel-ведомость финансиста), потому что в 1С полной картины нет.
